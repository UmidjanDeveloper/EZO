# EZO security

This document describes how EZO protects your data today and the rules contributors (human
or AI) must follow. If something here disagrees with the code, the code is wrong or this
document is stale: open an issue.

**Reporting a vulnerability:** do not open a public issue. Contact the repository owner
privately (GitHub profile of `UmidjanDeveloper`) with steps to reproduce.

## 1. Deployment model and authentication

- EZO is a **single-owner** assistant. `EZO_AUTH_MODE=local` (default) has no login and is
  only safe on your own computer. **Use `EZO_AUTH_MODE=token` with a long random
  `EZO_API_TOKEN` whenever anyone else can reach the API** (LAN, server, tunnel). The API
  refuses to start in token mode without a token.
- Every query is scoped to the owner's user id. Other users' or other projects' records answer
  `404`, never `403`, so their existence is not revealed.
- CORS allows only the origins in `EZO_CORS_ORIGINS`.
- Security headers are set on every response. Downloads use `Content-Disposition`
  (`attachment`, or `inline` for PNG previews only), `X-Content-Type-Options: nosniff` and
  `Content-Security-Policy: sandbox`, so uploaded or generated HTML/SVG never runs in the API's
  origin.
- Rate limits (in memory, per process): chat and voice `EZO_RATE_LIMIT_CHAT` (30/min),
  everything else `EZO_RATE_LIMIT_DEFAULT` (240/min). A Redis-backed limiter arrives with the
  worker (ROADMAP *Infrastructure*).
- Write actions (deletes, artifact changes, uploads, settings) are written to the audit log.

## 2. Secrets and AI-provider keys

- Secrets live only in `.env`, which is git-ignored. `.env.example` contains no values. The
  repository must never contain a key, token or password, including in tests.
- Settings hold keys as `SecretStr`. They are never logged, never returned by the API (the
  settings screen shows only *configured: yes/no*) and never sent to a model.
- Tool-call logs redact argument names containing `key`, `token`, `password`, `secret`,
  `authorization` or `cookie`. Orchestration events pass through `redact_secrets()`, which
  catches provider key formats, bearer tokens, JWTs, GitHub tokens and URL passwords.
- Keys are sent only to their own provider: Anthropic, OpenAI, Gemini, Tavily, and VoiceStudio
  if configured.
- External processes never inherit EZO's environment. A minimal environment is built
  explicitly (`orchestration/security.py: child_env`, `ruflo_env`).
- If a key leaks, revoke it at the provider first, then replace it in `.env`.

## 3. Uploads and files

- Size limit: `EZO_MAX_UPLOAD_MB` (25 MB, answered with `413`). Voice: `EZO_VOICE_MAX_AUDIO_MB`
  (10 MB).
- Type: an extension allow-list **plus content sniffing**, so a renamed executable is rejected.
  Archive formats (DOCX, XLSX) are checked for zip bombs.
- Filenames are sanitised, and storage keys are generated by EZO and validated against path
  traversal. The client never chooses a storage path.
- Duplicates are detected by SHA-256. Artifact versions are content-addressed and immutable.
- MIME types for downloads are decided by EZO from the extension allow-list, never by the
  client.
- Raw voice audio is **never stored**. It is transcribed in memory and discarded.
- Spreadsheet cells that start with `=`, `+`, `-` or `@` are neutralised to stop formula
  injection.

- Images (provider output and uploads to be edited) must decode as PNG, JPEG, WebP or GIF,
  ≤ 25 MB and ≤ 40 megapixels (checked before decoding). They are re-encoded to PNG, which
  drops EXIF/location metadata. SVG diagrams are served only as attachments under a
  `sandbox` CSP; only PNG previews are shown inline.

## 4. Model input (prompt injection)

- Text from files and web pages is wrapped as `<source n="…">…</source>` with an explicit
  "data, not instructions" rule. It is never placed in the system prompt as instructions.
- Citations are verified: numbers that do not match a real source are removed.
- Artifact IDs that a model writes into a presentation plan are discarded. EZO sets them
  itself and loads only image artifacts owned by the same user.
- An image provider's content-policy refusal is final: EZO never retries the request with
  another provider or a reworded prompt.
- Hidden model reasoning is never stored. Execution traces hold step names, timings and short
  summaries only.

## 5. Network and external tools

- Web fetching goes through `SafeFetcher`: http/https only, DNS resolved and **private,
  loopback and link-local addresses blocked** (SSRF), redirects re-checked, size and time
  limits. `EZO_FETCH_ALLOW_PRIVATE_NETWORKS=true` is for local development only.
- Tools run only through `ToolRegistry`: argument validation, timeouts, a `dangerous` flag that
  needs explicit user confirmation, and a logged `ToolCall` row for every run.
- There is **no arbitrary shell** reachable from the public API or from model output. The only
  subprocesses are fixed, argument-list commands in development scripts.
- Future DeveloperAgent tools (ROADMAP Phase 9) must stay inside an approved workspace. Path
  escape, system directories and secret files are blocked; push, deploy and destructive
  actions need approval.

- Official sources (LEX.UZ) are contacted only through `OfficialHttpClient`. It allows only
  the source's own hosts, obeys robots.txt (no fetch when robots.txt cannot be read), waits
  at least 5 s between requests and honours `Crawl-delay` and `Retry-After`. Any refusal
  (401/403/451) stops the run without retries or work-arounds. Sources whose access has not
  been reviewed cannot be enabled. See `docs/OFFICIAL_SOURCES.md`.
- OpenCode is evaluated only (not installed). The isolation rules a future integration must
  follow are in `docs/OPENCODE_INTEGRATION_PLAN.md`.

## 6. Approvals for external-impact actions

The following always need a human decision, whatever an agent or a model asks: Git push,
deploy, sending e-mail or messages, publishing, destructive deletes, spending money and
changing external accounts. The orchestration layer enforces this with approval gates (a step
waits in `waiting_for_user`). A confirmed delete in the UI is an explicit approval.

## 7. Dependency policy

- **Lockfiles are authoritative:** `apps/api/uv.lock` and `pnpm-lock.yaml`. CI installs with
  `--frozen` / `--frozen-lockfile`.
- **Audits** (`.github/workflows/security.yml`): `pip-audit` on the exported runtime lock and
  `pnpm audit --prod --audit-level high`. They run weekly, on every dependency change and on
  demand. They are kept separate from CI so a newly published advisory does not block
  unrelated work, but the run turns red.
- **Updates:** Dependabot (`.github/dependabot.yml`) only *opens* pull requests, grouped for
  minor and patch versions. **Major versions are ignored** and upgraded deliberately by hand,
  with the changelog read, all tests passing and Docker images rebuilt. Nothing is merged
  automatically. Never run `npm audit fix --force` or similar commands that apply breaking
  upgrades.
- New dependencies need a licence check first (THIRD_PARTY_NOTICES.md, OPEN_SOURCE_AUDIT.md).
  Copyleft (AGPL/GPL) code is never imported into EZO's process.
- To check locally:

  ```bash
  cd apps/api && uv export --frozen --no-dev --no-hashes --no-emit-project > /tmp/req.txt \
    && uvx pip-audit -r /tmp/req.txt
  pnpm audit --prod
  ```

## 8. Data at rest and backups

- Data lives in PostgreSQL (Docker volume `ezo-db`) and the storage directory (Docker
  volume `ezo-storage`: uploads, artifacts, exports).
- Neither is encrypted by EZO. Use disk encryption on the host if the machine can be lost.
- Backups are the owner's responsibility for now: `pg_dump` plus a copy of the storage volume.
  S3 storage and a documented backup/restore procedure are planned (ROADMAP *Infrastructure*).

## 9. Known gaps (honest list)

- Single-owner authentication only; no user accounts, roles or 2FA.
- In-memory rate limiter (one process).
- No malware scanning of uploads (only type and size checks).
- No encryption at rest inside EZO.
- No security review by a third party yet.

## Phase 3 — EZO Office security review (2026-10-18)

Reviewed: PDF engine, OCR, Word in-place editing, tables, spreadsheet operations, long
documents, chat attachments.

| Risk | Control | Verified by |
|---|---|---|
| Shell / command injection via OCR | Tesseract runs with a fixed argument list, `shell` never used, image bytes on stdin, minimal environment, timeout, 8 MB output limit; binary from server config (`EZO_TESSERACT_CMD` via `shutil.which`), never from a request | code review; `tests/unit/test_ocr.py` |
| Invented / injected language identifiers | packs must match `^[a-z]{3}(_[a-z]{3,4})?$` **and** be listed by `tesseract --list-langs`; `"uzb; rm -rf /"` is rejected | `test_language_packs_are_checked_not_invented` |
| Someone else's files | attachments are ownership-checked (404 `attachment_not_found`); every tool loads files through `load_file` with `user_id` checks; OCR and long-document caches are per user | `test_someone_elses_attachment_is_rejected` |
| Decompression bombs / oversized input | uploads: size limit, ≤ 5,000 zip parts, ≤ 200 MB unpacked; PDFs: 200 MB, 3,000 pages, render ≤ 40 M pixels, dpi ≤ 300; OCR ≤ `EZO_OCR_MAX_PAGES`; Word edits ≤ 50 MB and 400,000 characters; long documents ≤ 2,000,000 characters (refused, never cut) | unit tests |
| LibreOffice conversion (Word/Excel → PDF) | separate process: binary from config, fixed argv, no shell, fresh profile + temp dir per call, minimal env, timeout kills the process group, one at a time; files with external links (linked images, OLE, external data) are refused so the server never fetches URLs while converting | `tests/unit/test_office_convert.py` |
| Macros | `.docm` / `.xlsm` are not accepted; a `.docx` / `.xlsx` that contains `vbaProject.bin` is rejected at upload; openpyxl never runs macros | `test_macro_payloads_in_office_files_are_refused` |
| XML entity attacks | python-docx parses with `resolve_entities=False`; openpyxl uses the standard library parser, which has expat's billion-laughs protection | code review |
| Password-protected / restricted PDFs | never decrypted beyond an empty user password; files whose permissions forbid changes are refused for changes; signed PDFs get a "signature will be invalid" warning | `test_encrypted_restricted_and_corrupt_inputs_are_refused`, `test_signed_pdfs_get_a_warning` |
| Spreadsheet formula injection | text cells starting with `= + - @` are written as text (also for tables read from PDFs and scans) | `test_xlsx_numbers_headers_and_formula_safety` |
| Model output executing actions | model replies are only paragraph texts or validated `PdfStep` JSON (fixed operations, page-spec pattern); nothing is executed from free text | `test_steps_are_validated` |
| Prompt injection inside documents | document text is sent as data; EZO never follows instructions from it to call tools; outputs are written as text into the user's own new artifact | design |
| Originals modified | every operation writes a new artifact or version; inputs are read-only | integration tests check the upload size/hash afterwards |

Known residual risks:

- PDF parsing and rendering run in a worker thread. A tool timeout stops waiting for it,
  but cannot kill a pathological file mid-parse (Python threads cannot be cancelled). A
  separate worker process with a CPU limit is planned with the job system (Phase 5).
- OCR results can be wrong. EZO always labels OCR text as such and shows the engine's
  own confidence as a score, not as a probability.
